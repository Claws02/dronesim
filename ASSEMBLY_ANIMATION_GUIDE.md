# 3D Assembly Animation Guide

> **For AI assistants and authors.** This explains how to turn a 3D model of the drone into smooth "this piece goes here" animations inside the setup guide. You write **data, not code**: a list of steps saying which part moves, from where, and how.

## How it works (30 seconds)

1. The model is loaded in its **assembled** pose (the way CAD exports an assembly).
2. Each animation step names one or more **parts** (by their node names in the model) and an **action**.
   For the main action, `insert`, you say where the part comes **from** ("up", "out", "front"…). It then glides smoothly into its real position, with a dashed guide line, an arrow and a highlight glow.
3. Steps play in order with captions, and the reader can play, pause, scrub, step through, rotate and zoom.

```js
diagram: {
  type: "assembly3d",
  model: "placeholder-quad",
  show: ["frame_*", "arm_*"],                 // context parts visible from the start
  steps: [
    { label: "Motor 1 goes on the front-right arm", parts: "motor1", from: "up", callout: "Motor 1" },
    { label: "Then the other three", parts: ["motor2", "motor3", "motor4"], from: "up", stagger: 0.4 }
  ]
}
```

That's a complete, working animation. Put it in a step's `diagram` (or in `diagrams: [ ... ]` alongside a 2D diagram) in the `GUIDE` object of `index.html`.

## Files

| File | Role | Edit? |
|---|---|---|
| `assembly3d.js` | The player engine | No |
| `vendor/three.bundle.js` | three.js r187 + GLTF loader (MIT) | No |
| `models/placeholder-quad.js` | Procedural stand-in drone with realistic part names | Replace when real CAD arrives |
| `models/<name>.glb.js` | Your real model, wrapped for offline use | Generated by the tool below |
| `examples/x500/` | Real-CAD example: Holybro X500 from PX4's Gazebo models (BSD-3), plus the converter used to build it | Reference |
| `assembly-studio.html` | Authoring tool: load a model, see part names, test animations live | No |
| `tools/glb-to-js.mjs` | Converts `.glb` into an offline `.glb.js` wrapper and lists part names | No |

The guide loads these files **only** when a step with a 3D diagram is opened. If they're missing, that step shows a short notice and the written instructions still work.

## Getting a real model in

1. **Export from CAD as GLB (binary glTF).** SolidWorks, Fusion 360, Onshape and Inventor can all do this, directly or via Blender.
   - **Name the parts** you want to animate (e.g. `motor1`, `arm_fr`, `fc`). Node names become the `parts` names.
   - Keep it as an **assembly** with each animated piece as its own node (or group). Sub-parts nested under a group move with it.
   - Use Y-up (glTF default). Units can be anything (metres, mm). Offsets use the model's units.
   - No Draco compression (Meshopt compression or none is fine). Aim for under ~5 MB: decimate screws and threads.
2. **Wrap it for offline use:**
   ```bash
   node tools/glb-to-js.mjs exports/drone.glb drone --out models/drone.glb.js
   node tools/glb-to-js.mjs exports/drone.glb --list      # prints every part name, nested
   ```
3. Add `"models/drone.glb.js"` to `GUIDE.settings.models` and use `model: "drone"`.
4. Open `assembly-studio.html`, pick the model, and check the parts table for names, sizes and centres. Click on the 3D model to identify a part.

> Why the wrapper? Browsers refuse to fetch `.glb` files from a page opened by double-click (`file://`). A `.js` wrapper loads fine. On a web server (e.g. GitHub Pages) you can also use `model: "models/drone.glb"` directly.

## Shrinking a heavy model

CAD exports are often 10–50 MB, which is too heavy for a guide. Aim for **under ~5 MB**. Use [glTF-Transform](https://gltf-transform.dev) (free, open source), and run the steps individually:

```bash
npx @gltf-transform/cli weld    drone.glb s1.glb          # merge duplicate vertices (big win on CAD exports)
npx @gltf-transform/cli prune   s1.glb    s2.glb          # drop unused/empty nodes and materials
npx @gltf-transform/cli meshopt s2.glb    drone-small.glb # Meshopt compression (the player decodes it)
# optional, if still heavy:  npx @gltf-transform/cli simplify s2.glb s2b.glb --ratio 0.5 --error 0.001
```

> ⚠ **Don't use `gltf-transform optimize`** with default settings. It *joins and flattens* meshes, which merges your parts and **deletes the part names** the animations depend on. Also avoid `draco` (the player doesn't include a Draco decoder).

## Lessons from testing with real CAD

Tested end to end with the **Holybro X500** from PX4's official Gazebo models (`examples/x500/`, BSD-3). What real files threw at the pipeline, and what handles it now:

| Problem in the real file | Symptom | Handled by |
|---|---|---|
| Blender scene **lights and cameras** inside the meshes (16 point lights at ~14 million intensity) | Whole model rendered blown-out white | Player now ignores embedded lights/cameras (`modelLights: true` keeps them); `glb-to-js.mjs` warns |
| **Texture-only materials** whose image files weren't shipped | Parts render plain white | `glb-to-js.mjs` lists them; give them a base colour in CAD/Blender |
| 19.5 MB, 251k triangles, non-indexed geometry | Slow load | weld + prune + meshopt gave **19.5 → 3.0 MB with all names kept** |
| Geometry grouped **by material**, not by part (all carbon fibre = one mesh) | Can't move "the landing-gear legs" separately from "the arms" | Must be fixed at export: **export per part/body** (see below) |
| Z-up source data (Gazebo/ROS) | Model lies on its side / faces wrong way | Convert to glTF Y-up / −Z-front at export, or set `up` and `front` in the config |
| Auto-generated names (`MeshInstance_1_3`) and duplicates | Hard to address parts | Name parts in the export; `--list` shows duplicates |

**Export checklist for whoever supplies the CAD:**
1. One node per physical part or sub-assembly that moves during assembly. Name them (`arm_fr`, `motor1`, `fc`…).
2. Real base colours on every material (no texture-only materials unless the textures are embedded).
3. No lights or cameras in the export.
4. Y-up, front = −Z (glTF default), or tell the guide which way is up/front.
5. Binary GLB, then shrink it (above) and run `node tools/glb-to-js.mjs your.glb --list` before writing animations.

## Config reference

### Top level

| Key | Default | Meaning |
|---|---|---|
| `type` | | Always `"assembly3d"` inside the guide |
| `model` | | A built-in builder name (`"placeholder-quad"`), a registered model name (from a `.glb.js`), or a URL to a `.glb` |
| `steps` | `[]` | The animation steps (below) |
| `show` | all | Only these parts (plus every animated part) are visible. Best way to show "the drone so far" |
| `hide` | none | Parts never shown |
| `ghost` | none | Parts drawn see-through, as context |
| `labels` | `{}` | `{ partName: "Label" }`, used by `callout: true` |
| `camera` | auto-fit | `{ position:[x,y,z], target:[x,y,z] }` or `{ direction:[x,y,z], zoom:1.5 }` |
| `front` / `up` | `"-z"` / `"+y"` | Which axis is the drone's front and up. Makes "front", "left" and so on mean the right thing |
| `distance` | 0.7 × model radius | Default travel distance for word directions |
| `height` | 380 | Viewer height in px |
| `autoplay` / `loop` | true / true | Turned off automatically for users who prefer reduced motion |
| `hold` | 0.4 | Pause (s) after each step |
| `loopDelay` | 1.8 | Pause (s) before the loop restarts |
| `ground` | true | Soft shadow under the model |
| `modelLights` | false | Keep lights/cameras embedded in the model (normally they're ignored) |

### Step fields

| Key | Applies to | Meaning |
|---|---|---|
| `label` | all | Caption shown under the 3D view. Write it as an instruction: "Slide the arm into the slot" |
| `parts` | all except camera/wait | A name, a `*` wildcard (`"motor*"`, `"arm_*"`) or an array |
| `action` | | `insert` (default) · `remove` · `move` · `spin` · `highlight` · `show` · `hide` · `fade` · `camera` · `wait` |
| `from` | insert | Where the part starts: a word direction **or** an exact offset `[x, y, z]` in model units |
| `to` | remove, move | Where the part ends up (same formats) |
| `distance` | word directions | How far (model units). Defaults to the top-level `distance` |
| `path` | insert, remove, move | Waypoints `[[x,y,z], …]` (offsets from the part's home) for curved, natural motion, e.g. "come in from the side, then drop down" |
| `rotate` | insert, remove, move | `[x°, y°, z°]` starting rotation for insert (it unwinds to 0), or the end rotation for remove/move |
| `spin` | any moving action, `spin` | `{ axis: "y", turns: 2 }`: rotates while moving (screws, props, antennas). Negative = the other direction. For a Y-up model, positive turns about `y` = counter-clockwise seen from above |
| `duration` | | Seconds (default 1.2; camera 1.6) |
| `stagger` | multiple parts | Delay between each part starting (s) |
| `delay` | | Extra wait before this step starts |
| `with` | | `"previous"` runs at the same time as the previous step, with no new caption |
| `ease` | | `out` (default for insert), `inOut`, `in`, `linear`, `snap` (slight overshoot that "clicks" into place) |
| `callout` | | `true` (uses `labels`/part name) or a string. A pill label follows the part |
| `highlight` | | Glow while moving (default true; false to disable) |
| `trail` | | Dashed guide line + arrow (default true for insert/move) |
| `hideAfter` | remove | Fade out at the end (default true) |
| `opacity` | fade | Target opacity 0–1 |
| `camera` | any step | Camera move that plays with this step: `{ focus: "fc", zoom: 1.8 }`, `{ zoom: 1 }` (back out), `{ position, target }`, `{ direction:[x,y,z] }` |
| `hold` | | Pause after this step (s) |

### Direction words

`up`, `down`, `left`, `right`, `front` (`forward`), `back` (`rear`), combined with spaces (`"up front"`). Plus:

- **`out`**: radially outward from the model's centre, horizontally. Perfect for arms, motors and anything mounted around the edge. Each part uses its own direction.
- **`in`**: the opposite of `out`.
- Axis form: `"+y"`, `"-x+z"`.

## Recipes

```js
// Exploded → assembled (whole build in one view)
steps: [
  { label: "Arms",        parts: "arm_*",   from: "out", stagger: 0.15 },
  { label: "Electronics", parts: ["esc", "fc"], from: "up", stagger: 0.3 },
  { label: "Motors",      parts: "motor*",  from: "up", stagger: 0.2 }
]

// Screw something in: travel + spin
{ label: "Screw in the standoffs", parts: "standoff_*", from: "up", distance: 40, spin: { axis: "y", turns: 3 }, stagger: 0.1 }

// Slide in from the side, then drop (curved path)
{ label: "Slide the battery under the strap", parts: "battery", from: [0, 30, 120], path: [[0, 30, 40]], duration: 1.6 }

// Zoom in on a detail, then back out
{ label: "Check the arrow points forward", action: "highlight", parts: "fc_arrow", callout: "FRONT", camera: { focus: "fc", zoom: 2 } },
{ action: "camera", label: "Back to the full view", camera: { zoom: 1 } }

// Take something off (maintenance / swap steps)
{ label: "Remove the props", action: "remove", parts: "prop*", to: "up", spin: { axis: "y", turns: -2 } }

// Two things at once
{ label: "Fit both antennas", parts: "rx_antenna", from: "back" },
{ parts: "vtx_antenna", from: "up", with: "previous" }
```

## Rules for good visual aids

1. **One idea per step, caption = instruction.** The caption should match the written step text.
2. **Use `show`** so each step shows exactly "the drone so far": parts from earlier steps as context, future parts hidden.
3. **Match the real motion.** Things that screw in should spin. Things that slide into slots should approach along the slot (`path`). Things that click on can use `ease: "snap"`.
4. **Keep it short:** 2–5 steps per guide step, under ~10 seconds total.
5. **Callouts for orientation:** arrows, "FRONT", motor numbers, CW/CCW.
6. **Never invent geometry.** If the real model lacks a part, leave it out and note it in the step's `verify`.
7. Test every animation in `assembly-studio.html`. Its warnings list unknown part names, actions and directions. In the guide, open `index.html?edit` to see the same warnings under each 3D view.

## JavaScript API (optional)

```js
const player = Assembly3D.mount(element, config, { debug: true, onStep: (i, cap) => {}, onPick: info => {} });
await player.ready;
player.play(); player.pause(); player.seek(2.5); player.goStep(1);
player.setConfig(newConfig);   // re-run with a new animation, same model
player.parts;                  // [{ name, type, size, center, parent }]
player.issues;                 // config warnings
player.inspect();              // live per-part state (debugging)
player.destroy();
Assembly3D.registerModel("name", "data:…" or URL);
Assembly3D.registerBuilder("name", THREE => object3D);   // procedural models
```

## Rebuilding the three.js bundle (rarely needed)

```bash
npm install three esbuild
# entry.js: import three + GLTFLoader, OrbitControls, RoomEnvironment, MeshoptDecoder and assign them to window.THREE
npx esbuild entry.js --bundle --minify --format=iife --outfile=vendor/three.bundle.js
```

The player only uses `THREE.*` core classes plus `THREE.GLTFLoader`, `THREE.OrbitControls`, `THREE.RoomEnvironment` and `THREE.MeshoptDecoder`.
